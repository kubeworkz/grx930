# GRX930 Test Chip — wafer.space GF180MCU

Stripped-down GRX930 test chip targeting the wafer.space GF180MCU shuttle.

## Design Summary

| Feature | Value |
|---------|-------|
| Process | GF180MCU 180nm |
| Slot | 1×1 (full) |
| Die size | 3.93mm × 5.12mm |
| Core area | 12.92 mm² |
| I/O pads | 56 default, up to 168 |
| Clock | 50 MHz |
| Supply | 5V |
| Quantity | 1,000 bare dies |

## What's Included

- **RV64IMAC core** — 5-stage in-order, compressed ISA, single core
- **2KB I-cache + 2KB D-cache** — Tiny BRAM-based caches
- **2KB on-chip SRAM** — Boot/data memory (replaces DDR; the RTL is
  `grx930_sram_64kb`, shrunk to 256 × 64-bit words by the Plan B work)
- **UART (16550)** — Debug output at 115200 baud
- **GPIO** — 4-bit heartbeat LED output
- **External interrupt** — Single interrupt input
- **Boot ROM** — 1 KB at `0x0001_0000` (`grx930_test_chip_rom`, generated by
  `tools/gen_bootrom.py` from `../sw/test_chip_boot.hex`)

> **The chip boots standalone.** `CORE_RESET_PC` is `0x0001_0000`, the ROM's
> base, and the ROM holds the whole 272-byte firmware — so the core fetches real
> code from a read-only constant table on power-up, with no preloaded SRAM and
> nothing external. `make sim SIM_PLUSARGS=+NO_PRELOAD` (no SRAM preload) boots
> and reports `RESULT: PASS`; the negative control
> `make sim SIM_PLUSARGS=+NO_PRELOAD SIM_DEFS=-DROM_DISABLE` must report
> `RESULT: FAIL` with zero UART bytes, which is what proves the boot comes from
> the ROM.
>
> The ROM is constant combinational logic, not a memory with initial contents:
> a flop-init ROM would not survive synthesis into a netlist OpenROAD can place
> (see the generated file's header). It presents the SRAM's exact 2-cycle,
> 256-bit-line read interface and is selected by an address-range mux in
> `grx930_test_chip.sv`, and it holds its line past the done pulse because the
> I-cache controller samples the fill one cycle *after* completion.
>
> `c930_bootrom.sv` / `bootrom_wrapper.sv` remain in the tree but unused (the
> OL2 run drops both as unreachable, and `boot.hex` is only a four-word loop).

## Memory Map

```
0x0000_0000 – 0x0000_07FF : 2KB SRAM (code, data, stack; higher addresses alias)
0x0001_0000 – 0x0001_03FF : Boot ROM — 1 KB, read-only, CORE_RESET_PC (boots the part)
0x4000_1000 – 0x4000_100F : UART (16550, AXI4-Lite)
```

## Simulation

`make sim` boots the chip from RTL and fails if it does not boot:

```bash
cd c930/asic_gf180mcu
make sim                                     # RTL boot test, ~18 s
make sim SIM_CLK_FREQ=50000000               # at the part's real clock
make sim SIM_PLUSARGS=+NO_PRELOAD            # ROM-only boot (matches silicon)
make sim SIM_PLUSARGS=+NO_PRELOAD SIM_DEFS=-DROM_DISABLE   # negative control: must fail
make sim_gate                                # same test on the netlist (needs the PDK cell models)
make fw                                      # rebuild the hex AND the ROM from it
make check_rom                               # is the checked-in ROM in sync with the hex?
```

- Testbench: [`../tb/tb_grx930_test_chip.sv`](../tb/tb_grx930_test_chip.sv). It
  releases reset, then checks that the UART sends `GRX930 OK\n` at the DUT's own
  divisor, that the firmware's store/load-back pair reads back `0x2A5A_1234` at
  SRAM `0x400`, that the completion marker `0x0000_C0DE` is at `0x408`, and that
  the heartbeat counter is advancing. `RESULT: PASS`/`RESULT: FAIL` plus a
  non-zero exit status, which the Makefile turns into a failed target. The core
  runs from the ROM in every run; by default the testbench also preloads the
  2 KB SRAM with `../sw/test_chip_boot.hex` as extra state, and `+NO_PRELOAD`
  drops that to match a part that powers up with an empty SRAM.
- Firmware: [`../sw/test_chip_boot.S`](../sw/test_chip_boot.S) (272 bytes), built
  by [`../sw/build_test_chip_fw.sh`](../sw/build_test_chip_fw.sh) with a RISC-V
  toolchain; the checked-in hex is the current build. It is `-march=rv64ima` with
  `.option norvc`, so a failure is never a compressed-decoder question, and it
  polls `STATUS.tx_fifo_full` before every character so the run exercises MMIO
  reads interleaved with I-cache fills.
- The RTL is `openlane2_rtl/src` (the tapeout tree the OL2 flow reads), not
  `../rv64imac/RTL` — the two differ by the cache index/tag and MMIO read-hold
  fixes. **They also differ in chip top:** `make synth`/`make pnr` here still read
  the root `grx930_test_chip.sv` with `../rv64imac/RTL`, which is the width-5
  cache configuration, while the shuttle netlist is built from
  `openlane2_rtl/src` at width 4. Worth unifying.
